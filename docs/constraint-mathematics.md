# Constraint mathematics

Vocabulary and formulation for the shared illustrator constraint runtime.
Behavioral contracts live in OpenSpec capabilities (`geometry-ir`, `state-vector`,
`system-assembly`, `constraint-catalog`, `solve-interaction`, `solver-port`,
`system-architecture`, `display-mesh`). This document aligns the math terms with those specs.

## Glossary

| Term | Meaning |
|------|---------|
| **Document** | Discrete sketch (geometries, structural constraints, connectivity) plus a **committed** State. Independent of GUI and of any concrete solver algorithm. **Structural sync point:** add/remove geometry updates graph and State together (kinds only pack initial chart parameters). Evaluate/assemble take Document as geometry resolution plus an explicit State (committed or working). |
| **State** $p$ | Role name for the contiguous parameter vector (degrees of freedom). Length matches the Document's parameter count. The Document holds a **committed** \(p\); Interact/solvers use **working** copies of the same kind. In linux-rust the owned buffer type is `vector::Vector` (also used for the assembled residual \(r\)); roles stay in names (`p` vs `r`), not in distinct types. |
| **Chart (kind)** | Kind-owned packing of initial parameters and formula catalog for that geometry kind. Does not mutate Document or State by itself. |
| **Parameter window** | Contiguous index range on a geometry record (offset + count) identifying that geometry's slots in State; evaluate/formulas read \(p\) through this window. |
| **Vec2 / free vector** | Displacement or direction in the plane. Fundamental linear quantity: difference of points, segment direction, etc. |
| **Point2 / point** | Affine location. May be written as a position vector relative to an origin, but is not a free vector. $P - Q$ is a vector; $P + v$ is a point; $P + Q$ is not meaningful. |
| **HeadingAngle** | Absolute orientation from a fixed planar null ray (radians). Analogous to `Point2`: $\theta - \phi$ is a turn; $\theta + \tau$ is a heading; $\theta + \phi$ (two headings) is not meaningful. No wrap at the type level. |
| **TurnAngle** | Free angular displacement (radians). Analogous to `Vec2`: independent of the angle origin. linux-rust: `HeadingAngle` / `TurnAngle` replace an undifferentiated `Angle` DOF. |
| **World coordinates** | Durable planar frame for Document State and Mesh edge positions. **y-up** (scientific/mathematical): $+y$ points upward. Not window pixels. |
| **Viewport** | App/UI session mapping between world and screen coordinates: uniform scale, origin, and y-flip for toolkits with $+y$ downward. Paint uses world→screen; pointer input and pixel pick radii use screen→world (`r_{\mathrm{world}}=r_{\mathrm{px}}/\mathrm{scale}`). |
| **Point expression** | Opaque handle to a (private catalog of) **point formula**(s): a map from geometry State parameters to a 2D **point**. Not a free-standing point entity and not a coordinate snapshot. Geometry kinds construct formulas (e.g. segment start/end / on-curve); constraints and Interact only evaluate them — they do not match on formula kinds. |
| **Point formula** | Concrete eval / parameter indices / Jacobian for one point expression. Owned by a geometry kind; linux-rust uses per-formula structs (`StartPoint`, `EndPoint`, `OnCurve`, …) behind a private kind enum and opaque `PointExpr`. |
| **Point Jacobian** | Analytical $2\times n$ derivative of a point formula ($n$ = formula-local parameter count, sparse vs full geometry block). Rows are $\partial x/\partial p$ and $\partial y/\partial p$. linux-rust: expressions `accumulate_jacobian` into a `DenseMatrix` window (operands placed via `block_slice`). |
| **GeometryShell** | Shared document identity and State-block offset on each chart instance (linux-rust: `geometry/shell.rs`). Kind instances expose it via local `AsShell` (generated by `geometry_shell_instance!`). |
| **IdGenerator** | Document-owned allocator for non-colliding `GeometryId` (`allocate` / `observe`). Chart pack does not assign ids; `Document::add_geometry` allocates, import paths observe. |
| **GeometryInst** | Closed document catalog of geometry kinds (linux-rust: `geometry_kinds/catalog.rs`). Document stores `HashMap<GeometryId, GeometryInst>` (no `dyn`). |
| **GeometryKind** | Marker bound for a concrete kind: `Chart` + `AsShell` + `From<GeometryShell>` (+ Clone/Debug). `Document::add_geometry` requires `GeometryKind + Into<GeometryInst>`; shell helpers after storage live on `GeometryInst`. |
| **ConstraintInst** | Closed document catalog of structural constraint kinds (linux-rust: `constraint_kinds/catalog.rs`). Document entries hold `ConstraintInst` (no `dyn`). |
| **GeometryStore** | Read-only port: resolve `GeometryId` → `&GeometryInst` (linux-rust: `store.rs`). |
| **Mapper** | Chart layout: param block, unpack from State, local→global index lift via `GeometryShell.param_offset` (linux-rust: `mapper.rs`). Expressions resolve via GeometryStore, then unpack via `InGeometryCatalog` + Mapper; kinds stay in local indices. |
| **Vector expression** | Opaque handle to a map from geometry parameters to a free **vector** (e.g. segment direction, curve tangent or normal). Same opacity principle as point expressions; kind-owned formulas behind an outer kind sum. |
| **Scalar expression** | Opaque handle in a **typed** scalar family (length, heading angle, or turn angle). Same opacity principle; kind-owned formulas; analytical \(1\times n\) Jacobian written into a `DenseMatrix` window. linux-rust: `LengthExpr`, `HeadingAngleExpr`, `TurnAngleExpr` (no untyped `ScalarExpr` / single `AngleExpr`). |
| **Curve length** | Total arc length of a curve as a scalar expression (`length_expr` on the curve capability). Segment: Euclidean distance between endpoints. Circular arc: \(|R|\,|\Delta\theta|\). |
| **Normalized curve parameter** | Chart coordinate \(t \in [0,1]\): the curve's native formula domain affinely mapped to the unit interval. Equal \(\Delta t\) need not mean equal arc length. |
| **Uniform curve parameter** | Arc-length fraction \(u \in [0,1]\): equal \(\Delta u\) means equal arc length along the curve. For a line segment, and for a circular arc with constant \(|R|\), Normalized and Uniform coincide. |
| **Curve tangent** | Chart derivative \(\gamma'(t)\) as a free vector; length is parametric speed (segment: segment length). Not required to be unit length. |
| **Curve normal** | Leftward planar rotate of the tangent \((-v_y, v_x)\); same length as the tangent. Not a curvature-weighted vector. |
| **Residual** | Scalar (or small vector) that is zero iff a constraint (or soft term) is satisfied within tolerance. |
| **Local Jacobian** | Derivatives of a local residual contribution w.r.t. the local parameters that contribution depends on. |
| **Connectivity** $M_N$ | Explicit map from local parameter indices of contribution $N$ to global indices in $p$. Used to scatter local residuals/Jacobians into global arrays. |
| **Assembly** | Building the global residual $r(p)$ and Jacobian $J(p)=\partial r/\partial p$ by evaluating each contribution and scattering via connectivity. |
| **Soft contribution** | Transient residual used only during Interact (e.g. mouse follow, stay-near-previous, soft curve-length floor). Not stored as a structural constraint in Document. Weighted relative to structural residuals via soft-term weights (not a separate global hard-row rescale). |
| **Mesh** | View-layer tessellation of Document evaluated at a State \(p\) into drawable edges (tagged with geometry identity and role) in **world coordinates**. Derived only — not authoritative for parameters or constraints. Used for Canvas paint (via Viewport) and optional WYSIWYG hit-testing. Built with a **MeshFilter** that may omit construction geometries. Open curves are sampled via on-curve evaluation with adaptive subdivision until the tangent turn per parameter interval is at most a global max chord turn (linux-rust: `MAX_CHORD_TURN`); higher curvature ⇒ denser chords. Endpoint hit-testing uses geometric start/end only, not intermediate polyline vertices. |
| **GeometryRole** | Document flag on each geometry: **Result** (published figure) or **Construction** (helper). Construction remains in State and constraints; role alone does not remove parameters. |
| **Presentation mode** | App/UI session choice: result-only vs include-construction. Selects the MeshFilter for paint, Mesh hits, and logical handles so invisible construction is not pickable. |
| **Working copy** | Temporary State used during Interact / solve iterations. May differ from the committed State. |
| **Commit** | Replacing the Document's committed State with a working State after a successful solve (structural residuals within tolerance). |

## Design decision: opaque expressions (Model B)

**Choice:** `PointExpr`, `VecExpr`, and `ScalarExpr` are opaque newtypes over a **private** closed formula catalog (outer sum by geometry kind; shared capability tags). Constraints and Interact never match on formula kinds; they only call `evaluate` / connectivity / Jacobian helpers. Geometry kinds construct expressions via capability traits (`CurveExprs`, `EndpointExprs`) and kind factories (`start_expr`, `on_curve_expr`, `tangent_expr`, `length_expr`, …).

**Why:** Call sites should see “a point/vector map”, not `Endpoint | OnCurve | …`. A small fixed catalog stays data-driven (`PartialEq`, `Copy`, easy Debug/serde) without exposing variants. True openness (trait objects / closures) was tried and rejected for this codebase in favor of this facade — see approaches below.

**Consequences (linux-rust):** Kind-agnostic formula tags (`PointFormula`, `VecFormula`, `LengthFormula`, `HeadingFormula`, `TurnFormula`) in `geometry/capabilities.rs`; each kind implements `Chart` (via `chart_atoms!`) and `Geometry` (value / Jacobian / connectivity per formula family) under `geometry_kinds/<kind>.rs`; `Formula` connects a tag family to that triple. Opaque `Expr<F>` (`PointExpr` / `VecExpr` / `LengthExpr` / `HeadingAngleExpr` / `TurnAngleExpr`) in `expr.rs` resolves the id to `&GeometryInst` once, then dispatches on the data-less `GeometryKind` via `with_kind!`. Formula Jacobians write into `DenseMatrix` windows (`accumulate_jacobian`; vector jets + `contract_into` for \(g^\top J_v\)). Document stores closed catalogs `GeometryInst` / `ConstraintInst` (no `dyn`) in `IdMap`s. Shared affine types in `geom` (`Point2`/`Vec2`, `HeadingAngle`/`TurnAngle`, `Length`); owned `Vector` in `vector.rs`; `DenseMatrix` / `BlockSparseMatrix` in `matrix.rs`. Constraints never match on formula kinds.

### Approaches considered

Conceptually a point expression is always a map \(\mathrm{State}\to\mathrm{Point2}\) (plus connectivity / Jacobian). The approaches differ in **where the formula lives** and **whether the system has a fixed formula catalog**. All of them need a stored carrier that can later `evaluate` / report indices / Jacobians **without** holding a live `&Segment` — constraints outlive the call that created the expression.

#### A. Closed enum on `PointExpr`

```text
PointExpr = StartPoint { geometry } | EndPoint { geometry } | OnCurve { geometry, param }
evaluate / jacobian = central match on those constructors
```

| Pros | Cons |
|------|------|
| Simple `PartialEq` / `Debug` / (de)serialize — data only | Every new map kind touches the enum and every central `match` |
| Easy to read in the IR: you see the formula kind | Suggests a domain taxonomy of “point kinds” even though constraints only need a black box |
| Cheap sparsity choices per variant (e.g. endpoint uses 2 params, not 4) | Formula knowledge sits in `geom`/`PointExpr`, not with the geometry that owns the chart |

This was the first linux-rust shape. Fine while there are only two constructors; does not scale with more geometries.

#### B. Opaque newtype + private enum

Public API hides variants; only geometry factories construct `PointExpr`. Internally still a closed enum and a private `match`.

| Pros | Cons |
|------|------|
| Call sites match the mental model (`seg.end_point()` → `PointExpr`) | Same maintenance cost as A for new formula kinds |
| Constraints never pattern-match on kinds | Still a global (just private) catalog |
| Keeps data-driven Eq / Debug / serde | Opacity is API-only; openness is not real |

Sweet spot when the set of maps stays small and you want a clean surface plus data-driven equality — **chosen for linux-rust**.

#### C. Collapse to a single constructor (`OnCurve` only)

Endpoints are \(t=0\) / \(t=1\) (allowed by the curve model). One code path for eval / Jacobian.

| Pros | Cons |
|------|------|
| Fewer variants, one analytical path | Connectivity/sparsity may pull all curve params (e.g. 4) even for an endpoint that only needs 2 — unless optimized specially |
| Aligns with “everything is a chart sample” | Still a closed schema if other non-chart maps appear later (intersections, projections, …) |

Useful simplification *inside* a geometry; not a full answer once maps are not only on-curve samples.

#### D. Open trait + per-formula structs

```text
trait PointFormula { eval; param_indices; jacobian; eq_formula }
PointExpr = Arc<dyn PointFormula>
SegmentEndpointFormula / SegmentOnCurveFormula / …
```

| Pros | Cons |
|------|------|
| New geometry adds a type; no central expression `match` | Extra named types per map (noise if the math already lives on `Segment`) |
| Constraints see only the trait | `PartialEq` needs `eq_formula` (or similar); serde harder |
| Clear place for captures (`end`, `param`) | Easy to reinvent a second ontology of formula *names* |

First open-formula implementation after leaving the enum.

#### E. Open trait + closures (current)

```text
PointExpr::from_closures(geometry, key, eval, indices, jacobian)
Segment::start_expr / end_expr / on_curve_expr build those closures
```

| Pros | Cons |
|------|------|
| Formula bodies can sit next to `Segment` math; no per-map structs | Closures are not `PartialEq` → need an explicit equality `key` |
| Same openness as D for constraints | Debug/serde still awkward (key + geometry id, not the code) |
| Factories on the geometry remain the public constructors | Captures and vtable costs are less obvious than plain data |

Tried briefly in linux-rust; superseded by **B** (opaque + private enum) for simpler `Copy`/`PartialEq` and no equality keys.

#### F. Function pointers + plain data

A small POD payload plus `fn` pointers (or a table) for eval / indices / Jacobian.

| Pros | Cons |
|------|------|
| Eq/Debug over the POD; no fat trait object | Eval functions still need a shared signature and somewhere to live |
| Open if new rows register without editing `PointExpr` | More ceremony than closures for little gain in this crate |
| Friendly to FFI-shaped backends | Easy to drift back into a central registry of fns |

#### G. Geometry-local private enum

`PointExpr` stays opaque/open at the system boundary; **Segment** (or each geometry) keeps a *private* tag enum for its own maps and dispatches locally.

| Pros | Cons |
|------|------|
| Catalog is local to the geometry that owns the charts | Each geometry invents its own dispatch |
| No global `PointExpr` variant list | Cross-cutting maps (e.g. intersection of two geometries) do not fit one local enum |
| Data-driven Eq inside that geometry | Hybrid: open externally, closed per type |

Compatible with D/E as an *internal* detail of one geometry; not a substitute for an open handle at the constraint layer.

### Summary

| Approach | Catalog | Where formula lives | Best when |
|----------|---------|---------------------|-----------|
| A Closed `PointExpr` enum | Global, public | Central matches | Tiny fixed set of maps |
| B Opaque + private enum | Global, hidden | Central matches | Same, cleaner API |
| C `OnCurve` only | Global, tiny | Central / curve API | All maps are chart samples |
| D Trait + structs | Open | Per-formula types | Many maps, explicit types OK |
| **E Trait + closures** | Open | Geometry factories | Many maps, math on geometry |
| F fn + POD | Open/registry | Function table | FFI / POD-heavy hosts |
| G Local private enum | Per geometry | Geometry dispatch | Internal to one kind |

**linux-rust choice: B** (was briefly E). Shared public API: geometries construct expressions; constraints and Interact only evaluate opaque handles.

## Structure versus values

Document's discrete graph answers *what* exists and *how* it is wired.
State answers *where* continuous parameters currently sit. The Document owns
both the graph and a committed State \(p_{\mathrm{committed}}\).

Evaluation of geometry and constraints always takes Document (for identity
resolution) plus an explicit State $p$ (committed or working), so Interact can
try candidates without mutating the graph or the committed \(p\).

## Local geometry maps

A geometry $G$ has local parameters $p_{\mathrm{loc}} \in \mathbb{R}^{n_G}$
identified with a **contiguous block** of the global State via connectivity:
indices \(o, o+1, \ldots, o+n_G-1\) for a block offset \(o\) owned by the
geometry record in Document. Distinct geometries do not share
entries of \(p\); coincidence is a constraint residual, not index aliasing.
(If a future layout needs non-contiguous maps, the index list still belongs
on the geometry record — see OpenSpec `state-vector`.)

Example (line segment): local parameters
$(x_a,y_a,x_b,y_b)$. Endpoint expressions:

$$
\begin{aligned}
E_{\mathrm{start}}(p_{\mathrm{loc}}) &= (x_a, y_a), \\
E_{\mathrm{end}}(p_{\mathrm{loc}}) &= (x_b, y_b).
\end{aligned}
$$

Example (circular arc): local parameters
$(c_x,c_y,R,\theta_0,\Delta\theta)$ with radius $R$, start heading
$\theta_0$, and sweep turn $\Delta\theta$. $R \ge 0$ in committed State: the
solver may produce $R < 0$ in iterates (the parameter is unconstrained, and the
chart below is smooth through $R = 0$), and committing rewrites such an arc to
the identical curve $(c_x, c_y, -R, \theta_0 + \pi, \Delta\theta)$. The radius
expression evaluates to $|R|$. Chart:

$$
\begin{aligned}
\theta(t) &= \theta_0 + t\,\Delta\theta, \\
\gamma(t) &= (c_x, c_y) + R\,(\cos\theta(t),\sin\theta(t)), \\
L &= |R|\,|\Delta\theta|.
\end{aligned}
$$

linux-rust kind `Arc` also exposes `start_heading_expr` / `sweep_expr` as
typed angle expressions over the chart atoms.

Analytical derivatives of these maps w.r.t. $p_{\mathrm{loc}}$ feed constraint
Jacobians (see `geometry-eval`).

## Constraints as residual factories

A structural constraint $C$ produces a local residual $r_N$ of fixed arity.
Examples from the v1 catalog:

- **Congruence** of two point expressions $A(p), B(p)$:  
  $r = A(p) - B(p) \in \mathbb{R}^2$.
- **Parallel** of two segment direction vectors $u,v$: one scalar measuring linear dependence (e.g. the 2D cross $u_x v_y - u_y v_x$).
- **Orthogonal**: one scalar $u \cdot v$ (dot of free vectors).
- **FixPoint** of expression $A(p)$ to target $t$:  
  $r = A(p) - t \in \mathbb{R}^2$.
- **EqualLength** of two scalar expressions $s_a(p), s_b(p)$:  
  $r = s_a(p) - s_b(p) \in \mathbb{R}$ (typically curve `length_expr`s).

Each contribution also exposes derivatives equivalent to a contribution
Jacobian $J_N = \partial r_N / \partial p_{\mathrm{loc}}$ whose columns follow
that contribution's connectivity order. Assembly may pack $J_N$ then scatter,
or write formula Jacobian blocks straight into global $J$ via connectivity
(linux-rust: \(J\) is a `BlockSparseMatrix` with one dense row block per
contribution, built once per solve by `SystemEval::new_jacobian` from the
contribution connectivities; each contribution writes its \(J_N\) into its
block's dense submatrix (no scatter on write); formulas write via
`DenseMatrix::set_scaled` / `accumulate_jacobian` / vector jets with
`contract_into` (stack scratch for \(g^\top J_v\)); successive operand blocks
use `block_slice`. Difference residuals pass scale \(\pm 1\). Solver eval fills
owned `Vector` \(r\) and `BlockSparseMatrix` \(J\); the LM reuses evaluation
scratch within a solve.)

## Assembly (FEM-style)

Let contributions $N = 1,\ldots,M$ have local residuals $r_N$ and connectivities $M_N$.
The global residual stacks (scatters) them:

$$
r(p) = \operatorname{assemble}\bigl(r_1(p),\ldots,r_M(p);\; M_1,\ldots,M_M\bigr) \in \mathbb{R}^{m}.
$$

The global Jacobian is the scatter of contribution derivative blocks:

$$
J[M_N^{\mathrm{row}}(i),\, M_N^{\mathrm{col}}(j)] \mathrel{+}= (J_N)_{ij}.
$$

The \(+=\) matters: if one contribution's connectivity lists the same global
parameter twice (e.g. Congruence between start and end of one arc), both local
columns add into that global column.

Because the system is nonlinear, $r$ and $J$ are re-evaluated at the current $p$
whenever the solver requests them (`system-assembly`).

## Soft terms and Interact

During a drag (or similar manipulation), Interact forms an augmented residual

$$
r_{\mathrm{interact}}(p) = \begin{bmatrix} r_{\mathrm{structural}}(p) \\ r_{\mathrm{soft}}(p) \end{bmatrix},
$$

where $r_{\mathrm{soft}}$ may include:

- mouse-follow toward a pointer (weighted; via an opaque point expression),
- stay-near-previous toward the last consistent State,
- a one-sided soft length floor per curve, $\sqrt{w}\,\max(0,\ell_{\min}-L)$,
  with $\ell_{\min}=f\,L_0$ and $L_0$ the curve length at drag start (scale-invariant fraction $f$, not a fixed absolute length).

Soft terms are session-only (not stored in Document). Their strength relative
to unweighted structural residuals is carried by soft weights (linux-rust:
`SoftTerms` → per-term `.weight`, residual scale $\sqrt{w}$), not by
rescaling structural rows in assembly.

Structural parts are **hard** for commit: a successful commit requires
$\|r_{\mathrm{structural}}(p)\|$ within solve tolerance. Soft parts are
best-effort and are discarded when the gesture ends.

## What is minimized

The SolverPort drives updates to a working State by repeatedly evaluating
$r(p)$ and $J(p)$ (or an agreed equivalent). Typical owned backends minimize
a nonlinear least-squares objective such as

$$
\min_p \; \tfrac{1}{2}\,\|r_{\mathrm{interact}}(p)\|_2^2
$$

(e.g. Levenberg–Marquardt), but specs do **not** mandate a named algorithm—
only the interaction contract (invariants, soft drag, fail-keeps-committed-state).

On success, Interact **commits** the working State into the Document.
On failure, the committed State is left unchanged.

## Structural edits and $p$

Adding a geometry appends its contiguous parameter block to State and records
connectivity (block offset + parameter count). Removing a geometry
rebuilds/compacts State, remaps remaining block offsets, and drops constraints
that referenced the removed geometry id. Constraints store stable geometry
identities; raw indices in $p$ are always derived via connectivity.
